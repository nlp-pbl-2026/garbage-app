# 公開リポジトリの安全性と残作業

2026-11-15の監査とコード修正の記録です。今回AWSの設定変更・再デプロイ、秘密鍵の更新、Git履歴の書き換えは行っていません。以下の対策が公開APIへ反映されるのは、レビュー・マージ後に既存の安全なLambdaデプロイ手順で更新した後です。

## 今回のコード変更

### 認証API

- `SECRET_KEY`の固定フォールバックを廃止。32 UTF-8バイト以上の鍵が未設定なら、認証ルートは503を返し、登録処理も行いません。十分にランダムな鍵を環境変数／秘密管理で渡し、値をGit・ログ・公開Flutterへ置かないでください。
- チェックは認証境界で行います。検索・healthは鍵なしでも動き、検索専用Lambdaには認証ルーター・DB・bcrypt依存を追加しません。LambdaにJWT用環境変数を追加する必要もありません。
- 登録・ログイン・パスワード変更とハッシュ関数で、bcryptの72 **バイト**制限を検証します。日本語などは文字数とバイト数が違います。72バイトを超える入力はHTTP 422とし、切り詰めて認証しません。
- JWTは署名アルゴリズム、期限とsubjectの存在、整数ユーザーIDを確認します。既定鍵を過去に使用した認証環境では、別途安全に鍵を更新し、その鍵の既存トークンを失効させてください。今回既存の認証情報・ユーザーDBは変更していません。

ローカルで認証も使う場合、例えば次のコマンドで**値を画面へ出さず**一時的な鍵を設定できます。シェルを閉じると失われ、次回別の鍵を作ると旧トークンは使えません。継続運用では同じ鍵を安全な秘密管理から供給します。

```bash
export SECRET_KEY="$(python3 -c 'import secrets; print(secrets.token_urlsafe(32))')"
# このシェルからローカルFastAPIを起動する。鍵をechoしない。
```

旧実装で72バイト超のパスワードを登録したローカル利用者は、そのパスワードでログインできなくなります。旧実装では末尾が区別されなかったため、その互換性は維持しません。利用状況を確認して安全なパスワード再設定を行い、DB全体を削除して解決しないでください。

ログアウト／パスワード変更時の全JWT失効、短期アクセストークンと更新トークン、Webでの安全な保存方式、クラウド認証ルート・HTTPSへの接続は別設計として残します。既存トークンの7日期限は今回変更していません。公開Webのログインがlocalhostを参照する制約も残り、今回クラウド認証を有効化しません。

### `/decide`の検索根拠とサイズ

- 既存のJSON項目は維持します。現在のFlutterは`/retrieve`の文書をそのまま`/decide`へ送るため、クライアント改修や追加のモデル呼び出しは不要です。
- サーバーの対象自治体・profileのCSVから、URIの品目IDに対応する正規の本文を作り直して照合します。本文改ざん、未知ID、他自治体／旧profileのURI、重複根拠はモデル呼び出し前に422で拒否します。任意のURLを取りに行く処理はありません。
- 中島の公式例と共通索引からの地域別変換も同じ公式ルールで再構成します。公式例だけの利用時に、共通CSV・索引を新たに必須化しません。他自治体の根拠を代用しません。
- POST `/api/search/*`の実本文は5 MiB以下。Content-Lengthだけでなくストリーム実測でも制限し、JSON/base64処理より前に413で拒否します。CORSヘッダーも維持します。
- 根拠は最大20件、本文は各4,000文字、title 500文字、URI 1,000文字、根拠全体はUTF-8で64 KiB、scoreは有限の0〜1に限定。画像1枚・3 MiB、質問500文字等の既存制限も維持します。
- 現行の20市町・43profileのCSVでは本文最長439文字、最大の20行合計は19,606 UTF-8バイトで、制限を通ることを確認しています。

候補の順位・scoreを検索リクエストへ署名で結び付けるところまでは実装していません。正規の別品目を候補に選ぶ行為やプロンプトインジェクションを全面的に防止したとは扱いません。必要なら署名付き検索結果、またはサーバー内部で完結する`/classify`へのクライアント移行を別途設計します。

現在の公開設定は`USE_BEDROCK_KNOWLEDGE_BASE=false`です。任意の管理Knowledge Baseチャンク／S3 URIをクライアントから渡す旧実験用の段階APIは、原本照合できないため拒否します。KB方式を再採用する場合は署名付き根拠などを別途設計し、段階APIの互換性を再検証してください。サーバー内部で取得から判定まで実行する`/classify`の検索経路は維持します。

### 検索統計と個人情報

自由入力の質問・言い換え・追加回答・生成回答・追加質問・画像・詳細地区は保存しません。自治体ID、検索状態、公式区分、確信度、所要時間、収集日、画像の有無／形式／サイズ等の集計用メタデータだけを許可リストで保存します。検索ログサービスで再度フィルターし、INFOログにも自由入力文を出しません。検索処理途中の入力文・モデル出力や外部エラー本文のログ出力も除きます。

分析APIのキー保護、件数・区分別集計・確信度・処理時間、`recent`配列の形は維持します。旧Flutterでも表示できるよう、`query`には「（入力文は保存していません）」、`rewritten_query`には空文字を返します。直近の原文を読む分析機能は提供しなくなります。利用者への検索回答自体は従来どおり返します。

質問・画像は検索処理のために従来どおりAWSのモデルへ渡します。ログ保存の削減を、外部送信がなくなる変更とは扱いません。

既存JSONL・DynamoDBの原文は今回削除・書き換えませんが、分析APIへ返す際にも伏せます。保存済み原文やCloudWatchログを消したことにはならないため、保持義務・必要性を確認し、別途承認の下で削除／マスキングを判断してください。既存のDynamoDB TTL 90日・CloudWatch 30日という定義も変更していません。TTLは即時削除の保証ではありません。AWS SDKの詳細なリクエスト本文を出すDEBUGログは本番で有効化しないでください。

### 公開データとGit

松山市の既存NPZをローカルに保持したまま追跡解除し、`data/regions/**/*.npz`で入れ子のprofileも除外します。DBのサイドカーファイル、実設定のtfvars、IDEのworkspaceも除外対象に追加しました。manifest・生成／検証処理・地区台帳は保持します。実データ・索引の再生成、他自治体のデータ変更は行いません。

**他PCでこの変更を取り込む前にNPZを退避してください。** 削除コミットの適用で、以前追跡されていたファイルが作業ツリーから消える場合があります。取り込み後は同じパスへ戻してmanifestのSHA-256と照合します。[松山市データの配置手順](data.md#松山市索引の追跡解除と既存pcの注意)も参照してください。新規cloneのバックエンド用NPZは、他市町と同じくmanifest対応の共有物が必要です。無断で有料生成しません。

資料の利用・再配布条件は全20市町とも未確認の記録を維持します。公開APIの有効化を許諾確認済みという意味には変更しません。加工CSVやベクトルであれば自動的に公開可能とも判断しません。

## AWS側の濫用・費用対策（別途承認後）

公開APIは無認証で、URLやOriginを隠しても利用制限になりません。ブラウザへ埋め込む固定APIキーも秘密になりません。今回の本文制限は無制限な一件入力への対策であり、リクエスト数や総額を制限する仕組みではありません。

1. まずAPIリクエスト数・429・Lambda同時実行／時間・Bedrock使用量・費用のメトリクスを確認し、通知先と緊急停止の担当者を決める。原文ログは不要。Cost／Budgets通知には集計遅延があり、厳密な請求上限にしない。
2. `/rewrite`・`/retrieve`・`/decide`・`/classify`のレートとburst、Lambda reserved concurrencyを利用状況から決める。現行5 req/s・burst 10はTerraform定義上の値で、今回実環境を再取得していない。reserved concurrencyの設定自体に追加料金はないが、値を下げると正当な利用者も429／待ち時間の影響を受ける。0は緊急停止になる。provisioned concurrencyとは別で、性能対策として有料のprovisionedを自動追加しない。
3. 必要なら匿名セッション／認証と利用者・IP単位の回数制限、日次のモデル呼び出し予算をサーバー側へ追加する。共有カウンターをDynamoDB等に置く場合は追加読み書き料金・保持情報・誤検知・停止解除手順を別途設計する。Lambdaプロセス内のカウンターでは複数インスタンスを制限できない。
4. WAFを検討する場合、現在のAPI Gatewayは **HTTP API** で、AWS WAFを直接関連付ける対象のREST APIとは異なる。CloudFront等の対応する入口と、直接API URLからの迂回防止を一緒に設計する。現在の静的Web DistributionへWAFを付けるだけでは、別URLへ送る検索APIリクエストは保護されない。

| 対策 | 追加費用・運用上の注意 |
| --- | --- |
| HTTP APIの既存throttle調整 | 既存APIの呼び出し料金は継続。制限はベストエフォートで、利用者単位・金額上限ではない |
| Lambda reserved concurrency | 設定自体の追加料金なし。処理・Bedrock料金は継続し、総額を止めるものではない |
| Budgets／CloudWatch／通知 | 通常の監視用予算は無料。Budgets Actionsは別料金条件、CloudWatch alarms／SNS等は構成・使用量で課金。自動停止は遅延・誤停止と解除手順を考慮する |
| WAF従量制の基本構成例 | Web ACL 1つ US$5/月、ルール1つ US$1/月、100万リクエストあたりUS$0.60が基本例。API用入口・ログ・CAPTCHA・追加ルール等は別。料金・プラン・地域条件を導入時に再確認する |

API応答中断のタイムアウトだけでは、別スレッドのモデル呼び出しが即座に止まる保証もありません。モデル使用量を監視し、緊急停止を実施・復旧できる運用にしてください。WAF、認証、回数制限、監視／通知設定はいずれも今回のAWS変更対象に含めません。

根拠: [HTTP APIスロットリング](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-throttling.html)、[Lambda reserved concurrency](https://docs.aws.amazon.com/lambda/latest/dg/configuration-concurrency.html)、[WAF対応リソース](https://docs.aws.amazon.com/waf/latest/developerguide/waf-chapter.html)、[WAF料金](https://aws.amazon.com/waf/pricing/)、[Budgets料金](https://aws.amazon.com/aws-cost-management/aws-budgets/pricing/)。
