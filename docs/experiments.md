# あいまいごみ分別検索 実験レポート

「品名が分からないごみ」を自然な言葉から正しい分別区分へ分類できるかを評価する。
提案手法（地域データに接地した **Titan Embedding RAG**）を、素の大規模言語モデル（ChatGPT/GPT-5.6）と比較した。
対象地域は自治体データの差し替えで拡張できる設計だが、本実験では一例として松山市のデータを用いた。

## 1. 実験設定

### 対象・正解ラベル
- 対象自治体: 松山市（清水地区）。
- 正解ラベル: 松山市『ごみ分別はやわかり帳（家庭用）』由来の `data/regions/matsuyama/common/knowledge/items.csv`（1,756品目、品目名・分類コード・注意事項・出典ページ付き）。
- 分類コード（9区分）: 可燃 / 埋立 / 金・ガ / 紙類 / ペット / プラ / 水銀 / 粗大 / 禁止。

### 評価データセット
- items.csv を品目単位で層化分割（train/test 非重複、seed 固定）し、**test 30件**で評価。
- 各ケースは、正解品目を隠して**わざと曖昧に言い換えたクエリ**（例: 「梱包の時に使うプチプチみたいなの」）と、追加質問に答えるための `hidden_context` からなる。
- 生成は Amazon Nova Lite で行い、**品質ゲート**（正解を伏せた往復同定＋レビュー）を通過したものだけ採用。
- データ矛盾が判明した1件（透明プラ容器なのに正解が金・ガ）は除外。
- 生成物は `backend/evaluation/artifacts/`（Git追跡外）。

### 比較したシステム
| 記号 | システム | 検索 | 判定LLM |
| --- | --- | --- | --- |
| A | **提案手法（現システム）** | Titan Embedding検索（松山市データに接地） | Amazon Nova Lite（AWS Lambda上） |
| B | GPT-5.6 + Web検索 | RAGなし。OpenAI Responses APIの`web_search`でWeb参照 | gpt-5.6-sol（reasoning=medium） |
| C | GPT-5.6 検索なし | RAGなし。パラメトリック知識のみ | gpt-5.6-sol（reasoning=medium） |

- B・C は「実際の利用シーン」を模し、`愛媛県松山市において「{クエリ}」は何ゴミに分類されますか？` と自然文で質問。
  自由文の回答を、事後的に別モデル（gpt-4o-mini）で9分類コードへマッピングして採点した（判定器は回答文を翻訳するだけで自前の分別知識では上書きしない指示）。
- A は言い換え→検索→判定→（必要なら）追加質問のパイプライン。追加質問には Nova が `hidden_context` に基づき回答（シミュレータ）。
- AWS本番はLambdaからTitan Text Embeddings V2を直接呼び出し、同梱した品目Embedding索引を検索する。`USE_BEDROCK_KNOWLEDGE_BASE=false`、`LEXICAL_SEARCH_ENABLED=false`でEmbedding単体へ固定している。

### 指標
- 分類精度（正解率）、平均応答時間、カテゴリ別精度、平均追加質問数。

### 前提・限界
- A と B/C は **LLMが異なる**（Nova vs GPT-5.6）ため、これは純粋なアブレーションではなく**システム同士の比較**である。「地域特化RAGを組む」対「素朴にChatGPTに聞く」の実利的比較と解釈する。
- 事後マッピングの判定器は回答文に忠実（後述の誤答は判定器の誤りではなく、モデルの回答自体が松山市の分類と異なる）。
- OpenAI APIのクレジット上限により、B・C は 30件での結果を最終値として採用（A のみ 50件でも 86.0% (43/50) を確認済み）。

## 2. 実験結果

### 主要結果（test 30件）
| システム | 精度 | 平均応答時間 |
| --- | ---: | ---: |
| **A. 提案手法（Nova + Titan Embedding RAG）** | **90.0%（27/30）** | **2.0 s** |
| B. GPT-5.6 + Web検索 | 86.7%（26/30） | 11.5 s |
| C. GPT-5.6 検索なし | 66.7%（20/30） | 12.5 s |

- 提案手法が最も高精度かつ最速。Web検索は素のLLM（C→B, 66.7%→86.7%）を大きく改善するが、地域特化RAG（90.0%）には届かない。
- 応答時間は提案手法が約6倍高速（NovaとTitanの軽量呼び出し vs GPTのreasoning＋Web検索）。

### 提案手法のカテゴリ別精度（A）
プラ4/4・ペット1/1・可燃4/4・埋立2/3・水銀4/4・紙類4/4・金・ガ2/3・禁止2/3・粗大4/4。

### 検索脚のアブレーション（Hybrid / Embedding単体 / Text単体）
提案手法のRAGは「表層一致検索」と「意味検索(Embedding)」を統合(RRF)している。
各脚の寄与を切り分けるため、**判定LLM(Nova)・プロンプト・追加質問シミュレータを固定**し、
検索の脚だけを入れ替えて同一の test 30件を評価した（すべてローカル実行・意味検索は自前Embedding索引）。

| 検索構成 | 精度 | 平均応答 | 内訳 |
| --- | ---: | ---: | --- |
| Hybrid（表層一致＋Embedding） | 86.7%（26/30） | 1.2 s | 誤分類4 |
| **Embedding 単体** | **90.0%（27/30）** | 1.2 s | 誤分類3 |
| Text（表層一致）単体 | 73.3%（22/30） | 1.2 s | **未確定6**＋誤分類2 |

考察:
- **意味検索(Embedding)が主たる貢献**。単体で90.0%と最も高く、あいまいな言い換え（例「風呂上がりに着るふわふわの服」）でも該当品目へ到達できる。
- **表層一致単体は弱い（73.3%）**。曖昧クエリでは品目名と文字列が重ならず**候補ゼロ→未確定**が多発（れんが・ピアノ・画用紙・財布・白熱電球など6件）。正式名に近い入力にしか効かない。
- **Hybrid(86.7%) は Embedding単体(90.0%) をわずかに下回った**。表層一致が正式名の近い誤候補を上位へ入れ、判定を惑わせる例（温度計・湿度計など）があったため。この結果を受け、公開環境もEmbedding単体を採用した。
- 本アブレーションはローカルの自前Embedding索引で実施した。公開Lambdaでも同じtest 30件を評価し、Embedding単体90.0%（27/30）、Hybrid86.7%（26/30）を確認した。

**意味検索の実装（自前Embedding vs Knowledge Base）で最適構成が逆転する点に注意**:
| 意味検索の実装 | Hybrid（＋表層一致） | Embedding単体 |
| --- | ---: | ---: |
| 自前Titan Embedding（ローカル） | 86.7% | **90.0%** |
| Knowledge Base（デプロイ環境） | **93.3%** | 83.3% |

- **自前Embedding**では単体が最良（表層一致が誤候補を混ぜて僅かに悪化）。
- **Knowledge Base**では表層一致との併用が最良で、単体にすると10pt低下（KBの意味検索は表層一致と相補的）。
- 運用上の結論: 自前Titan Embeddingを使える環境なら **Embedding単体**、Knowledge Baseで運用する場合は **Hybrid** が良い。本番はTitan直接呼び出し権限を取得できたため **Embedding単体**を採用している。

### 改善の推移（開発時 train 40件）
検索証拠の質を改善した効果は開発中の訓練セットでも確認できた。
- lexical（表層一致）のみ: 72.5% ※意味検索が権限エラーで不動だった状態
- ＋クリーンな意味検索（1品目=1レコード化）: 82.5%
- ＋判定プロンプトの分類原則追加: 90.0%

## 3. 誤答分析と考察

### 3.1 提案手法（A）の誤答（3件）
- **ピアノ（正解: 禁止 → 判定: 粗大）**
  「大きな木製の鍵盤楽器」から琴や鍵盤ハーモニカなどの粗大ごみ候補が上位となり、ピアノへ到達できなかった。品目同定の検索再現率が課題。
- **グリルパン（正解: 金・ガ → 判定: 粗大）**
  「網目のついた調理器具」から調理台や電磁調理器などを検索し、正解品目が上位候補に入らなかった。用途表現が広すぎる場合の検索失敗。
- **グラインダーの替刃（正解: 埋立 → 判定: 金・ガ）**
  「替刃」の大半（カッター・カミソリ・草刈機・芝刈機の替刃）は金・ガであり、グラインダーの替刃だけが埋立という**正解データ側の外れ値**。システムは多数派に沿って「金属の刃＝金・ガ」と一般化しており、判断としてはむしろ妥当。B・C も同じく誤答した。

### 3.2 GPT-5.6 + Web検索（B）の誤答（4件）
Web検索で松山市公式ページを参照できても、**クエリの曖昧さで品目を取り違える**、または**正解ラベルの粒度**に届かない例が中心。
- **グリルパン（金・ガ → 可燃）**: 「網目のついた調理器具」をGPTが**ざると誤認**し、素材次第（プラ/竹=可燃）と回答。品目同定の失敗。
- **血圧計・水銀式（水銀 → 粗大）**: 「血圧を測る機械」が曖昧で、GPTは一般的な**電子血圧計**を想定し粗大と回答。正解は水銀式（水銀）。クエリ曖昧＋ラベル粒度。
- **温度計・湿度計・水銀不使用（金・ガ → 粗大）**: GPTは**デジタル温湿度計＝小型家電＝粗大**と推論。松山市の該当品目は金・ガ。
- **グラインダーの替刃（埋立 → 金・ガ）**: 3.1と同じ外れ値。Web参照でも金・ガと結論。

考察: Web検索は正しい根拠に到達しても、**曖昧クエリからの品目同定**は依然弱い。提案手法は松山市データに直接検索をかけ、必要に応じ追加質問で素材・方式を確定できるため、この種の取りこぼしに強い。

### 3.3 GPT-5.6 検索なし（C）の誤答（10件）
パラメトリック知識のみだと、**一般常識に基づき自信満々に、しかし松山市の分別とは異なる**回答をする傾向が顕著。
- **白熱電球・ハロゲンランプ（水銀 → 埋立）**: GPTは「電球は不燃＝埋立、水銀を含む蛍光灯のみ水銀ごみ」と一般常識で回答。松山市はこれらを水銀区分とするため不一致。
- **コピー用紙（紙類 → 可燃）**: 「コピー用紙は可燃ごみ。紙製容器包装ではない」と断言。松山市では資源の紙類。
- **靴クリームの容器・プラ製（プラ → 金・ガ）**: GPTは**金属缶**を想定し金・ガ。実物はプラ製容器。
- **スプリングマットレス（禁止 → 粗大）**: 一般に粗大だが、松山市は市収集不可（禁止）。
- **ケイカル板／石膏ボード（埋立 → 禁止）**: GPTは建築廃材＝業者依頼（禁止相当）と回答。松山市は埋立。
- **電気コード（粗大 → 金・ガ）**、**洗濯物干し・タコ足（可燃 → 粗大）**、**血圧計（水銀 → 粗大）**、**グラインダー替刃（埋立 → 金・ガ）** 等。

考察: これらは「一般知識では妥当に見えるが自治体の分別とは違う」典型で、**RAGで地域資料に接地しなければ原理的に当てにくい**。提案手法が高精度な理由がここに表れている。

### 3.4 総合考察
1. **地域特化RAGの価値**: 素のLLM（C, 66.7%）に対し、Web検索（B, 86.7%）で大きく改善するが、自治体データに直接接地した提案手法（A, 90.0%）が最良。ごみ分別のような**自治体ごとに規則が異なるタスク**では、汎用知識やWeb検索より、対象データへの接地が効く。
2. **速度**: 提案手法は約2.0秒で、reasoning＋Web検索のGPT（約11–12秒）より約6倍高速。実運用の体感でも優位。
3. **残存課題**: (a) 曖昧な用途表現から正解品目を検索候補へ入れる再現率、(b) 正解データの外れ値（グラインダー替刃）。前者は索引テキストや検索クエリの改善余地、後者は原資料の粒度・一貫性の問題。
4. **限界**: 本比較はモデルが異なるためシステム比較である点、評価規模が30件である点、事後マッピング判定を用いた点に留意。

## 4. 再現手順
```bash
cd backend
# データセット生成
uv run python -m evaluation.build_dataset --train-limit 40 --test-limit 30 --seed 20260901
# 提案手法の評価
uv run python -m evaluation.run_evaluation --split test --limit 30
# GPTベースライン（要 OPENAI_API_KEY）
uv run python -m evaluation.run_openai_baseline --split test --model gpt-5.6-sol --reasoning-effort middle --web-search   # B
uv run python -m evaluation.run_openai_baseline --split test --model gpt-5.6-sol --reasoning-effort middle              # C
# 検索脚のアブレーション（要 items.csv と item_embeddings.npz）
uv run python -m evaluation.run_ablation --split test --mode hybrid --limit 30
uv run python -m evaluation.run_ablation --split test --mode embedding --limit 30
uv run python -m evaluation.run_ablation --split test --mode lexical --limit 30
```
生成物・レポートは `backend/evaluation/artifacts/runs/<run名>/report.md`（Git追跡外）。
