# Flutterの複数自治体対応

実際に選択できる自治体は松山市と八幡浜市です（[八幡浜市の対応範囲・収集日未確認の区分](yawatahama-data.md)）。架空の2自治体によるテストで、
同じ地区ID・分別設定ID・収集区分IDを使っても地域を混同しないことを確認します。
新自治体の公式データ取得・曜日規則の実日付展開・実機での検証は自治体追加時に行います。

## 共通原本と生成

入口はバックエンドと同じ `data/regions/catalog.json` と各自治体の `registry.json` です。
[バックエンドのデータ契約](multi-municipality-backend.md)に従って整備し、次を実行します。
API・AWS・Embedding生成は呼び出しません。

```bash
backend/.venv/bin/python scripts/generate_frontend_data.py
```

- `frontend/assets/data/municipality_catalog.json` に、登録自治体・台帳版・分別表示設定・参照先を生成します。
- 台帳は `municipality_{自治体ID}_registry.json`、カレンダーは `municipality_{自治体ID}_{番号}_calendar.json` です。
  同じ原本を参照する分別設定は同じカレンダーを共有します。
- 公式住所対応表 `data/regions/{自治体ディレクトリ}/generated/addresses.json` がある場合は住所表も複製します。
- 松山市は既存の `municipality_registry.json` / `municipality_calendar.json` / `municipality_addresses.json` を維持します。
- カタログと台帳メタデータはGit管理対象です。カレンダー・住所表はGit管理外の生成物です。
  CSV、NPZ、分類プロンプトはFlutterに同梱しません。
- `--catalog` と `--output` でテスト用の入力・出力先を指定できます。出力先は独立した生成物用ディレクトリを指定してください。

台帳とカタログの自治体ID・版を照合します。カレンダーは自治体ID・版・適用期間が一致し、
収集地区のカレンダーが `verification_status=checked` の場合のみ使用します。
未知の収集区分・壊れた設定・欠損ファイルを松山市の値で補いません。
未検証の日付・適用期間外の日付は収集予定にしません。欠損ファイルは画面で読み込みエラーになります。
生成処理そのものは公式PDFの正誤を検証しないため、原資料の照合は別途必要です。

APIにデータ版照合用のエンドポイントはありません。バックエンドとFlutterを同じ原本から
準備し、配布前に版とカレンダーファイルの一致を確認してください。不要な実行時同期・キャッシュは追加していません。

## 分別表示・収集予定

分類コードと収集区分を区別します。各 `rule_profiles.*.categories` の
`collection_type_id` がある分類だけをカレンダー・通知・iCalに使用します。
`cutoff` は `HH:MM` で、当日の次回収集判定・朝の通知・iCalの案内に共通して使います。
定期収集しない粗大ごみや持込対象を、名前だけでカレンダーに追加しません。
表示可能な期間も台帳から取得します。

任意のUI用項目として、分類定義内に `color: "#RRGGBB"` と `collection_name` を指定できます。
指定がない色は中立色を使います。表示名は `collection_name`、なければ分類の `name` です。
複数分類が同じ収集区分を指す場合は1区分にまとめ、最初の定義の表示名・色を使うため、
必要に応じて共通の `collection_name`・色を明示してください。搬出期限が食い違う定義は拒否します。
松山市は既存のカテゴリID・色・表示順・通知設定キーとの互換処理を残します。

## 地域選択・GPS・保存済み設定

市町村の選択肢は同梱カタログ、地区の選択肢は選んだ自治体の台帳です。
清水地区への既存ショートカットは、その地区が登録されている場合にだけ表示します。
保存済み地区は自治体IDと地区IDの組で検証します。未対応・曖昧な旧地区は再選択が必要で、
保存内容を勝手に削除したり別自治体へ読み替えたりしません。

GPSは逆ジオコーディング結果の都道府県・自治体名を照合したうえで、公式町名対応表から
候補を提示し、利用者が確認します。住所表には `municipality_id` と台帳と同じ `version`、
`entries: [{town, lookup_town, area_id}]` が必要です。対応表のない自治体では手動選択に案内します。
既存GeoJSON・旧地区番号から収集地区IDを推定しません。

自治体または地区の変更で、検索結果・追加質問・選択画像・選択日をリセットします。
実行中の古い検索結果も捨てます。通知の保存先・ペイロードには自治体と地区を含め、
別地域の通知から現在のカレンダーへ古い日付を選択しません。
通知カテゴリ設定は自治体と分別設定で区別し、松山市だけ旧設定の互換読み込みを行います。
通知の有効・無効と通知時刻は従来どおりアプリ全体の設定です。

## 粗大ごみ

松山・北条の戸別申込みと中島の地区別収集の互換案内は、自治体ID `38201` に限定します。
他自治体で `nakajima` という分別設定名を使っても、中島の案内を適用しません。
他自治体は専用APIの案内、または分別設定の任意項目 `bulky_waste` を利用できます。

- `config`: `MunicipalityConfig.fromJson` と同じ自治体案内JSON。自治体IDの一致を検査します。
- `category_code`: 品目一覧APIで使用する、その分別設定の分類コードです。
  省略時に松山市の「粗大」コードを他自治体へ適用しません。
- `collection_type_id`: 定期収集方式で、手動記録の日付を公式カレンダーで検証する場合に指定します。

案内が未整備なら未登録と表示します。料金・申込区分を推測しません。
手動記録は自治体IDと地区IDで区別し、旧記録の自治体ID省略は松山市として扱います。

## 検証

```bash
cd frontend
flutter test
flutter analyze
```

単体・画面テストでは架空自治体のAssetBundleとHTTPモックを使います。
自治体選択、同一IDの分離、検索3段階への地域情報の送信、言い換え・判定への画像・追加回答の送信、古い結果の破棄、
通知設定と通知予約の切り替え、搬出期限、iCal、GPS候補、粗大ごみ案内・記録を検証します。
生成処理は `backend/tests/test_frontend_data_generation.py` で別途検証します。

実GPS・通知権限と配信・OS共有シートは実機確認が必要です。Webでネイティブ通知の動作は確認できません。
この作業では実Bedrock・AWS APIを呼んでおらず、他19市町の公式データも追加していません。

## 一部の収集区分が未確認の場合

`verification_status: partially_checked` と全収集区分の `collection_type_verification` を読み込みます。
`unverified` の区分は日付を返さず、画面で「収集日未確認」と説明・公式資料へのリンクを表示します。
検索APIの追加項目 `collection_status` が `unverified` の場合も、次回日付を表示しません。
通知・iCalは確認済みの収集予定だけを使用し、未確認を「予定なし」と同一視しません。
既存のカレンダーと、追加項目のない旧API応答も読み込めます。

地区台帳に `display_name` がある場合は地区選択・保存済み設定の表示に使用します。省略時は `name` を使うため、松山市の既存表示は変わりません。表示名の更新でID・通知設定・カレンダーの対応を変更しません。一部区分の注意は地域選択の案内ではなく、該当する品目の検索結果やカレンダーの未確認区分の詳細で表示します。
